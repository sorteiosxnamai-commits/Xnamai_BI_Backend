# Revisão do código do ERP — 08/10/2026

Autorrevisão feita por quem implementou, depois de validar em PostgreSQL real. **Não substitui uma
revisão independente**; os pontos abaixo dizem onde olhar primeiro.

## Defeitos encontrados e corrigidos

| Área | Defeito | Correção | Teste |
|---|---|---|---|
| Financeiro | Baixas simultâneas de parcelas diferentes do mesmo título recalculavam o status do título sem trava (status podia ficar errado) | `SELECT … FOR UPDATE` no título em `settle`, `reverse` e `cancel_title` | concorrência em PostgreSQL |
| Financeiro | `cash_flow` agrupava por dia UTC e comparava limites sem converter: baixa às 22h BRT caía no dia seguinte (e o filtro de período errava) | dia civil de Brasília, limites convertidos para UTC antes do SQL | `test_cash_flow_groups_by_brasilia_day_not_utc` |
| Compras | Status do pedido após estorno parcial lia objetos ORM desatualizados (o `UPDATE` condicional não atualiza o que está em memória) | leitura direta das colunas | `test_partial_receipt_reversal_keeps_the_other_receipt` |
| Worker | Execução de sync deixada em `running` por crash ficava assim para sempre | a próxima execução do recurso a encerra como `interrupted` | `test_run_left_running_by_a_crash…` |
| Worker | Webhook "venenoso" (falha ao processar) era reprocessado indefinidamente | no máximo 5 tentativas, depois `failed` com o erro | `test_poison_webhook_stops_after_max_attempts` |
| Fila | Dois processos podiam enfileirar o mesmo job ao mesmo tempo | índice único parcial `uq_erp_jobs_active` + captura de conflito | `test_active_job_is_unique…` |
| Worker | Job longo não renovava o lease e podia ser reenfileirado enquanto rodava | heartbeat em tarefa paralela (lease/3) | revisão + teste de lease expirado |
| Dados pessoais | Detalhe de pedido (endereço de entrega, observações, extras), valores de conflitos de cliente e a intenção das operações vazavam para perfis sem `pii:read` (achado da revisão de segurança automática) | mesma regra do cliente: omitidos/`[restrito]` sem `pii:read` | `test_orders_conflicts_and_intents_hide_personal_data…` |
| Acesso | Login do BI vinculado a operador (`viewer` compartilhado) identificava "pessoas" por conta compartilhada | desligado por padrão; só o bootstrap entra pelo BI; operadores têm login próprio | `test_bi_logins_do_not_identify_people…` |

## O que foi examinado e está correto

- **Migração:** só `CREATE TABLE/INDEX` de `erp_*`. Subida, descida (volta ao head legado exato, sem
  alterar tabela/coluna legada) e subida de novo, **em PostgreSQL 16 real**, a partir do zero (cadeia
  legada + ERP). As constraints `CHECK` de saldo e baixa existem no banco, não só no modelo.
- **Permissões:** nega por padrão; chave de serviço do BI sempre 403; `*` só do administrador;
  aprovação de compra, autoridade do saldo, operadores, snapshots e auditoria são só `*`; dados
  pessoais mascarados sem `pii:read`; operações do outro operador invisíveis sem `integration:sync`;
  todas as consultas filtram por `connection_id`.
- **Movimentações financeiras:** baixa e estorno usam `UPDATE` condicional (`settled + x <= amount`);
  estorno é um novo registro, no máximo um por baixa; título com baixa não cancela; estorno de
  recebimento é atômico (estoque + quantidade + conta a pagar, tudo ou nada).
- **Estoque:** saldo só muda por `UPDATE` condicional (`on_hand + d >= 0`, `reserved <= on_hand`);
  evento causal único; razão imutável; reversão causal; ajuste é saldo absoluto com `expected_on_hand`.
  Verificado com 12 threads concorrentes em PostgreSQL: exatamente o saldo disponível é consumido.
- **Recuperação do worker:** lease vencida reenfileira só o que é idempotente (sync). Operação de
  escrita com `dispatch_started_at` gravado **antes** da chamada vira `unknown` após queda, nunca volta
  à fila; sem envio, volta à fila. Resultado gravado em outra transação, com 3 tentativas.

## Riscos residuais (conhecidos, não corrigidos)

1. **Bloqueio de conta como vetor de negação de serviço:** quem souber o login de alguém pode bloqueá-lo
   por 15 min errando a senha. Contraponto aceito para barrar força bruta; há auditoria e o admin
   pode redefinir. Considere limite por IP no gateway.
2. **CSRF no refresh/logout:** o cookie `erp_refresh` segue o `SameSite` do BI (`none` por padrão, por
   causa de frontend e backend em domínios diferentes). O corpo da resposta de `/auth/refresh` não é
   legível por outra origem (CORS com origens fixas), mas um site hostil poderia forçar *logout*.
   Mitigação: servir front e API no mesmo site e usar `SameSite=Lax/Strict`.
3. **Sem 2FA** e sem política de expiração periódica de senha.
4. **`ERP_JWT_SECRET` vazio** deriva a chave do `JWT_SECRET` do BI. Funciona e separa os tipos de
   token, mas defina um segredo próprio.
5. **A cota do Mercos** entre BI/ERP/agente continua dependendo do gateway (Prompt 1).
6. **Mapeamentos inferidos** (grade de produto, extras, faturamento, status) só se confirmam com a
   sondagem do sandbox.
7. O custo médio do estoque não é calculado (guarda o custo de cada recebimento).

## Como reproduzir a validação em PostgreSQL

```bash
pip install pgserver          # PostgreSQL embutido, só para testes; ou use qualquer Postgres isolado
ERP_TEST_DATABASE_URL=postgresql+psycopg://postgres@127.0.0.1:<porta>/postgres python -m pytest tests/erp
```

Cada teste recria o schema ERP; testes de concorrência e migração criam bancos próprios
(`erp_concurrency`, `erp_migration`, `erp_isolation`). **Nunca aponte para um banco com dados reais.**
